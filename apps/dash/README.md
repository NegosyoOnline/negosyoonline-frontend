# NegosyoOnline dashboard

The subscriber dashboard. Staging is `dash-staging.negosyonline.com` (Vercel project `negosyoonline-dash-staging`, deployed from `main`).

The dashboard is static HTML, CSS and JavaScript in `public/`, moved as is from the TWCinc `negosyoonline-dash` folder. Next.js only serves it: `next.config.ts` supplies the routing, the security headers and the CSP. It uses the API's HttpOnly session cookie, set when the visitor signs in on the public site, and shows only real API data. It holds no secrets.

## Pages

| Path | File | Purpose |
| --- | --- | --- |
| `/` and every dashboard section (`/orders/`, `/account/`, `/settings/billing/`, `/settings/general/`, `/settings/shipping/`, `/earnings/`, ...) | `public/index.html`, `assets/js/dashboard.js` and the per-section scripts | The dashboard. `dashboard.js` routes sections in the browser with the History API. |

Shared: `assets/js/app.js` (API client, shell, formatting), `assets/css/dash.css`, `assets/js/theme.js`.

## Routing

- Every path ends in a slash (`trailingSlash`); a path without it redirects to the slash form, query string kept.
- Real files and `/assets/js/config.js` are served first. Every other path serves `index.html`; an unknown path falls back to Overview in the browser.
- Pages are sent with `Cache-Control: no-store`. `/assets/*` is cached for an hour, so `index.html` loads each asset with a `?v=` token: bump the token of every file a release changes.

## Configuration

`/assets/js/config.js` is generated by `src/app/assets/js/config.js/route.ts` from environment variables read at build time (`src/lib/site-env.ts`):

| Variable | Default (staging) |
| --- | --- |
| `SITE_API_BASE` | `https://api-staging.negosyonline.com/v1` |
| `SITE_URL` | `https://www-staging.negosyonline.com` |
| `SITE_DASH_URL` | `https://dash-staging.negosyonline.com` |

The CSP `connect-src` follows `SITE_API_BASE`. Production must set all three. The API must list the dashboard origin in CORS.

The CSP allows images from one public Vercel Blob media host, set as `mediaOrigin` in `next.config.ts`. It must match the backend's public media host.

## Behaviour notes

- The session is the API's own HttpOnly cookie, sent with every call (`credentials: "include"`). Nothing is stored in the browser except the theme. A 401 sends the visitor to the public site, which opens its sign-in popup (`/?signin=1`). The dashboard has no login page.
- The API answers errors as `{error: {code, message, fields}}`; `app.js` converts that once into the flat shape the screens read.
- Site ids are opaque strings (`site_…`). `GET /sites/` answers `{items, next_cursor}`.
- Billing (`assets/js/billing.js`) calls `GET /sites/` and, per site, `GET /sites/{id}/billing/`, `billing/payment/`, `billing/payments/?limit=20`, `billing/payments/{id}/proof/`, `POST billing/payments/`, `POST billing/cancel/`, `POST billing/reactivate/`, `GET /plan/`, and, under Payment history, the owner documents (each card hidden when its route answers 404): `GET billing/statements/?limit=10&cursor=`, `statements/{number}/`, `statements/{number}/pdf/`, `GET billing/invoices/?limit=10&cursor=`, `invoices/{id}/copy/`, and `GET` and `PUT billing/profile/`. The PDF and the invoice copy are fetched with the sign-in cookie and shown from a blob URL. Payments (`assets/js/payments.js`) calls `GET /sites/` and `/sites/{id}/payment-methods/` (`GET`, `PATCH`, `POST` and `DELETE` on `accounts/`, `PUT` and `DELETE` on `xendit/`). Each shows its "could not load" panel if a call fails.
- Account Settings (`/account/`, `assets/js/account.js`) reads `GET /account/` and writes through the API: name, email change, sign out other devices, connect and disconnect Facebook and Google. The API keeps one `name`; the page splits it into its two boxes and joins them on save. Connecting leaves for the address the API answers with (Google or Facebook only) and returns to `/account/#connect=<provider>&result=<result>`. The mobile row calls `/account/mobile/*`, which the API does not serve yet.
- Statuses, dates, amounts and the referral link come from the API; the browser only formats them.

## Local preview

```bash
pnpm dev
```

Open http://localhost:3001. Signing in needs an API that lists this origin in `API_ALLOWED_ORIGINS`; the staging API does not list a local origin.

Tests for the client and onboarding helpers: `pnpm test` (`node --test`, no extra dependency).

## Inbox channels (G3 PR3)

`/inbox/` (`assets/js/inbox.js`) lists Facebook Messenger, website chat and email conversations in one list, each with a neutral channel badge, with a Channel filter in the house dropdown, Close and Reopen for the stored channels, delivery chips and the fixed failure texts of a reply, and the banners (chat paused, chat limit reached; one chat banner at a time, the limit first). `/settings/inbox/` (`assets/js/inbox-settings.js`) has the Inbox channels card (web chat switch, "Pause for", Pause chat, Resume chat) and the Email card (the contact-form switch only when the API sends `contact_inbox_available`). They read and write `/sites/{id}/inquiries/channels/`; a 404 there shows the page's "not available yet" notice. All API text reaches the page through `textContent`.
